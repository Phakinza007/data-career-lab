## API จะล้มเหลวเป็นเรื่องปกติ

เมื่อระบบเรียก LLM API หลายพันครั้ง สิ่งที่หนีไม่พ้นคือ: rate limit (HTTP 429), เซิร์ฟเวอร์ล่ม/โอเวอร์โหลด (5xx), timeout, เครือข่ายหลุด
ส่วนที่ทำให้แอปดูเป็นมืออาชีพคือการรับมือกับความล้มเหลวเหล่านี้ ไม่ใช่แค่เขียน prompt ให้เก่ง (ตัว SDK ส่วนใหญ่มี retry อัตโนมัติและตั้ง `max_retries` / `timeout` ได้ แต่คุณต้องเข้าใจหลักการ)

**บทนี้จำลองบริการที่ล้มเหลวด้วยฟังก์ชันของเรา** (ไม่ได้เรียก API จริง) เพื่อให้ฝึกและตรวจผลได้ซ้ำทุกครั้ง

## 1) Retry ด้วย exponential backoff

ลองใหม่เฉพาะข้อผิดพลาดที่ "ชั่วคราว" (429, 5xx, timeout) — ส่วน 400/401 (คำขอผิด/ไม่มีสิทธิ์) ลองกี่ครั้งก็ผลเดิม อย่า retry
รอนานขึ้นเป็นเท่าตัวทุกครั้ง (1, 2, 4, 8, …) จนถึงเพดาน และใส่ **jitter** (สุ่มลดเวลารอ) เพื่อไม่ให้ลูกค้าจำนวนมากกลับมาพร้อมกัน:

```python
def backoff_delays(attempts, base=1, cap=8):
    return [min(cap, base * 2 ** k) for k in range(attempts)]   # [1, 2, 4, 8, 8]

rng = random.Random(0)
jittered = [rng.uniform(0, d) for d in backoff_delays(5)]        # full jitter
```

ระวังการ retry คำขอที่ "มีผลข้างเคียง" (เช่น สั่งจ่ายเงิน) — ต้องมี idempotency key

## 2) Cache ผลที่ซ้ำ

คำถามเดียวกันด้วยพารามิเตอร์เดียวกันไม่ควรเสียเงินซ้ำ สร้างกุญแจจากคำขอทั้งก้อนแบบ deterministic:

```python
key = hashlib.sha256(json.dumps(request, sort_keys=True).encode()).hexdigest()
```

`sort_keys=True` ทำให้ dict ที่ลำดับ key ต่างกันได้กุญแจเดียวกัน · วัด **hit rate** = (คำขอทั้งหมด − คำขอที่ต้องเรียกจริง) ÷ คำขอทั้งหมด
ข้อควรระวัง: cache เหมาะกับงานที่ต้องการคำตอบเดิม (FAQ, สกัดข้อมูล) แต่ไม่เหมาะกับงานที่ต้องการความหลากหลาย และต้องมีอายุ (TTL) เมื่อฐานความรู้เปลี่ยน

## 3) Rate limiter และ circuit breaker

- **Sliding window**: อนุญาตได้ไม่เกิน N คำขอในช่วง W วินาทีที่ผ่านมา — ที่เหลือรอหรือปฏิเสธ
- **Circuit breaker**: หลังล้มเหลวติดกัน 3 ครั้ง "เปิดวงจร" หยุดยิงคำขอชั่วคราว ป้องกันการถล่มบริการที่ล่มอยู่และประหยัดเวลา/เงินของเรา แล้วค่อยลองใหม่ภายหลัง

หลักคิดรวม: ล้มเหลวเร็ว, ลองใหม่อย่างมีเงื่อนไข, ไม่จ่ายซ้ำโดยไม่จำเป็น, และบันทึก log ทุกครั้งที่ retry
