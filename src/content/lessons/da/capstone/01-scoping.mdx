## โจทย์ของ capstone นี้

module นี้ไม่มีเทคนิคใหม่ — ทุกอย่างที่ใช้เรียนมาหมดแล้ว สิ่งที่ฝึกคือ **การต่อทุกอย่างเข้าด้วยกันเป็นงานชิ้นเดียว**
ที่เอาไปใส่ portfolio และเล่าในการสัมภาษณ์ได้จริง

โจทย์ที่เราจะตอบตลอดทั้ง module:

> **ปี 2025 ร้านมีรายได้โตขึ้น 21% จากปี 2024 — การเติบโตนี้ยั่งยืนแค่ไหน และปีหน้าควรลงแรงต่อที่ไหน**

คำถามแบบนี้คือคำถามจริงที่ผู้บริหารถาม และมันยังตอบไม่ได้ในรูปแบบปัจจุบัน เพราะคำว่า "ยั่งยืน" กับ
"ควรลงแรงที่ไหน" ยังไม่ใช่สิ่งที่ query ได้ งานแรกของ DA จึงไม่ใช่การเขียน SQL แต่คือ **การแปลงคำถาม**

## แปลงคำถามกว้างให้เป็นคำถามที่ตอบได้

แตกคำถามใหญ่เป็นคำถามย่อยที่แต่ละข้อมีคำตอบเป็นตัวเลขชัดเจน:

| # | คำถามย่อย | ตัวชี้วัดที่ใช้ตอบ | ใช้ข้อมูลจาก |
| --- | --- | --- | --- |
| 1 | การเติบโตมาจากกิ่งไหนของ metric tree | revenue, orders, AOV, customers | orders, order_items |
| 2 | โตเพราะลูกค้าใหม่หรือลูกค้าเดิม | รายได้แยก new/existing | orders, order_items |
| 3 | ลูกค้าใหม่ที่ได้มา คุณภาพดีไหม | retention เดือนที่ 1 แยกช่องทาง | orders, customers |
| 4 | ช่องทางไหนคุ้มที่สุด | รายได้ต่อลูกค้าแยกช่องทาง | orders, order_items, customers |
| 5 | รายได้ที่โตขึ้น แปลว่ากำไรโตด้วยไหม | gross margin แยกหมวดสินค้า | order_items, products |
| 6 | มีจุดรั่วอะไรที่แก้แล้วได้ผลเร็ว | funnel drop-off, ผล A/B test | events |

ข้อดีของตารางแบบนี้คือทุกคนเห็นตั้งแต่ต้นว่าจะได้อะไรกลับไป และเราจะรู้ทันทีว่าข้อมูลที่มีพอตอบไหม
ก่อนจะลงแรงเขียน query

## profiling: รู้จักข้อมูลก่อนเชื่อข้อมูล

ก่อนวิเคราะห์อะไร ต้องรู้ก่อนว่าข้อมูลที่มีหน้าตาเป็นยังไง มีอะไรขาด และเชื่อถือได้แค่ไหน
ขั้นตอนนี้เรียกว่า **data profiling** — ใช้เวลาไม่นานแต่ช่วยไม่ให้เสียเวลาทั้งวันกับข้อสรุปที่ผิด

**1. ขนาดและช่วงเวลาของแต่ละตาราง**

| ตาราง | แถว | ช่วงเวลา |
| --- | --- | --- |
| customers | 3,300 | สมัคร 2024-01-01 ถึง 2025-12-15 |
| products | 120 | — |
| orders | 6,938 | สั่ง 2024-01-03 ถึง 2025-12-31 |
| order_items | 12,183 | — |
| events | 55,900 | **2025-01-01 ถึง 2025-12-31 เท่านั้น** |

สิ่งที่สะดุดตาทันทีคือ `events` มีแค่ปี 2025 — แปลว่า **คำถามข้อ 6 เทียบ funnel ระหว่างปีไม่ได้**
ต้องปรับคำถามเป็น "จุดรั่วของ funnel ปี 2025 อยู่ตรงไหน" แทน นี่คือเหตุผลที่ต้อง profiling ก่อนเขียนแผน
ไม่ใช่หลังจากเขียน query ไปครึ่งวันแล้ว

**2. ค่าว่างในคอลัมน์สำคัญ**

```sql
SELECT COUNT(*) AS rows,
       COUNT(customer_id) AS with_customer,
       COUNT(variant) AS with_variant
FROM events
```

`COUNT(คอลัมน์)` ไม่นับ NULL ต่างจาก `COUNT(*)` — เทียบสองค่านี้จึงบอกจำนวนค่าว่างได้ทันที
ผลคือ `events` มี `customer_id` แค่ 33,452 จาก 55,900 แถว (60%) และมี `variant` 31,948 แถว
(เฉพาะช่วงที่ทำ A/B test) ทั้งสองอย่างไม่ใช่ข้อผิดพลาด แต่เป็น**ข้อจำกัดที่ต้องรู้**:
วิเคราะห์ระดับผู้ใช้จาก events ได้ไม่ครบทุกคน

**3. ความสอดคล้องระหว่างตาราง**

```sql
SELECT COUNT(*) AS items_without_order
FROM order_items li
LEFT JOIN orders o ON o.order_id = li.order_id
WHERE o.order_id IS NULL
```

เช็คว่ามี "ลูกกำพร้า" ไหม — รายการสินค้าที่ไม่มีออเดอร์ ออเดอร์ที่ไม่มีลูกค้า ฯลฯ
ชุดข้อมูลนี้สะอาดในแง่นี้ (ได้ 0 ทุกกรณี) แต่มีอีกเรื่องที่ต้องรู้: **ลูกค้า 461 คนจาก 3,300 คน
ไม่เคยสั่งซื้อเลย** ถ้าคำนวณ "รายได้เฉลี่ยต่อลูกค้า" โดยหารด้วย 3,300 กับหารด้วย 2,839
(คนที่เคยสั่ง) จะได้คนละตัวเลขและตอบคนละคำถาม

**4. ตรวจตรรกะที่ต้องเป็นจริงเสมอ**

```sql
SELECT COUNT(*) AS orders_before_signup
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
WHERE o.order_date < c.signup_date
```

ออเดอร์ต้องไม่เกิดก่อนวันสมัคร ยอดต้องไม่ติดลบ เปอร์เซ็นต์ต้องอยู่ระหว่าง 0–100 — การตรวจแบบนี้
(เรียกว่า sanity check) ต้องทำก่อนเชื่อผลอะไรทั้งนั้น ชุดข้อมูลนี้ผ่านทุกข้อ

## ระบุขอบเขตและข้อจำกัดให้ชัดตั้งแต่ต้น

รายงานที่ดีบอกตั้งแต่ต้นว่า **อะไรอยู่ในขอบเขตและอะไรไม่อยู่** — ไม่ใช่ปล่อยให้คนอ่านไปเจอเอาเองตอนท้าย

**อยู่ในขอบเขต:** ยอดขายและออเดอร์ปี 2024–2025, พฤติกรรมบนเว็บปี 2025, ลูกค้าและช่องทางที่มา,
กำไรขั้นต้นจากต้นทุนสินค้า (`products.cost`)

**ไม่อยู่ในขอบเขต (เพราะไม่มีข้อมูล):**

- **ต้นทุนการตลาด** — ไม่มีตารางค่าโฆษณา จึงคำนวณ ROI หรือ CAC (ต้นทุนต่อการได้ลูกค้าหนึ่งคน) ไม่ได้
  พูดได้แค่ว่าช่องทางไหนสร้างรายได้ต่อลูกค้าสูงกว่า แต่ไม่รู้ว่าได้มาด้วยราคาเท่าไหร่
- **ค่าส่งและค่าธรรมเนียมการจ่ายเงิน** — กำไรที่คำนวณได้จึงเป็นกำไรขั้นต้น ไม่ใช่กำไรสุทธิ
- **funnel ปี 2024** — ตาราง events มีแค่ปี 2025

การเขียนข้อจำกัดไว้ล่วงหน้าไม่ได้ทำให้งานดูอ่อน ตรงกันข้าม — มันแสดงว่าเรารู้ว่ากำลังพูดถึงอะไรอยู่
และกันคำถามที่ตอบไม่ได้ในห้องประชุมไปได้เกือบหมด

## ลำดับการทำงานที่เหลือของ module นี้

1. **บทนี้** — ตั้งโจทย์ แตกคำถามย่อย และ profiling ข้อมูล
2. **บทที่ 2** — ตอบคำถามย่อยทั้ง 6 ข้อด้วย SQL แล้วรวมเป็นภาพเดียว
