## ข้อสรุปที่ผิดแต่ดูดี อันตรายกว่าการไม่มีข้อสรุป

บทที่แล้วเราได้ข้อสรุปมาแล้วว่า "การเติบโตปี 2025 ยังไม่ยั่งยืน" ซึ่งฟังดูสมเหตุสมผลและมีตัวเลขประกอบครบ
แต่ก่อนส่งให้ใคร ต้องผ่านการตรวจสี่แบบนี้ก่อน — เพราะเมื่อผู้บริหารตัดสินใจตามรายงานของเราแล้ว
ความผิดพลาดจะแพงมาก และคนที่ต้องตอบคำถามคือเรา

1. **กระทบยอด (reconciliation)** — ตัวเลขย่อยบวกกลับเป็นตัวเลขรวมได้ไหม
2. **ความไวต่อนิยาม (sensitivity)** — เปลี่ยนนิยามแล้วข้อสรุปยังเหมือนเดิมไหม
3. **นัยสำคัญทางสถิติ** — ความต่างที่เห็นใหญ่พอที่จะไม่ใช่ความบังเอิญหรือเปล่า
4. **ความทนต่อ outlier** — ตัดข้อมูลสุดโต่งออกแล้วผลยังเหมือนเดิมไหม

## 1. กระทบยอด: ตัวเลขย่อยต้องบวกกลับได้

การแบ่งข้อมูลเป็นกลุ่มด้วย `CASE WHEN` หรือ `JOIN` ทำให้แถวหายหรือซ้ำได้ง่ายมากโดยไม่มีอะไรฟ้อง
วิธีจับคือบวกกลับ:

```sql
WITH first_order AS (...), sales_2025 AS (...)
SELECT (SELECT SUM(line) FROM sales_2025) AS sum_of_parts,
       (SELECT SUM(li.quantity * li.unit_price)
        FROM orders o JOIN order_items li ON li.order_id = o.order_id
        WHERE o.status = 'completed' AND EXTRACT(year FROM o.order_date) = 2025) AS total_revenue
```

สองค่านี้ต้องเท่ากันเป๊ะ (17,829,346 ทั้งคู่) ถ้าไม่เท่า แปลว่าการ join ทำให้แถวหายไป
(เช่น ลูกค้าบางคนไม่มีใน `first_order`) หรือซ้ำขึ้นมา ต้องหยุดแล้วหาสาเหตุก่อน ห้ามเดินต่อ

เช็คแบบเดียวกันนี้ใช้ได้กับทุกตารางสรุป: ผลรวมรายเดือนต้องเท่ากับผลรวมรายปี ผลรวมของทุก segment
ต้องเท่ากับผลรวมทั้งหมด และสัดส่วนทุกกลุ่มรวมกันต้องได้ 100%

## 2. ความไวต่อนิยาม: เปลี่ยนนิยามแล้วเรื่องเปลี่ยนไหม

ข้อสรุปหลักของเราคือ "รายได้ปี 2025 มาจากลูกค้าใหม่ 84%" — แต่ "ลูกค้าใหม่" นิยามได้หลายแบบ
ลองเปลี่ยนนิยามดูว่าข้อสรุปยังยืนอยู่ไหม:

| นิยาม "ลูกค้าใหม่" | รายได้จากลูกค้าใหม่ |
| --- | --- |
| ซื้อครั้งแรกปี 2025 (ที่ใช้ในรายงาน) | 84.0% |
| สมัครสมาชิกปี 2025 | 82.0% |

ต่างกัน 2 จุด แต่ **เรื่องที่เล่าไม่เปลี่ยน** — ไม่ว่านิยามไหนก็ยังเป็น "รายได้ส่วนใหญ่มาจากลูกค้าใหม่"
ข้อสรุปแบบนี้เรียกว่า **robust** (ทนต่อการเปลี่ยนสมมติฐาน) และเป็นข้อสรุปที่ปลอดภัยพอจะเอาไปเสนอ

ถ้าเปลี่ยนนิยามแล้วผลพลิกจาก 84% เป็น 40% เรื่องจะต่างกันสิ้นเชิง และสิ่งที่ต้องทำคือ
**รายงานทั้งสองตัวเลขพร้อมบอกว่านิยามไหนให้ผลแบบไหน** ไม่ใช่เลือกเฉพาะตัวที่เข้าทางข้อสรุปของเรา

## 3. นัยสำคัญ: ความต่างนี้ใช่เรื่องบังเอิญหรือเปล่า

เราบอกว่าช่องทาง `promo` มี retention แย่กว่า `organic` ชัดเจน (7.3% เทียบ 22.4%)
แต่ `promo` มีลูกค้าแค่ 219 คน — กลุ่มเล็กแบบนี้ผันผวนได้มาก จึงต้องทดสอบด้วย
**two-proportion z-test** เหมือนที่ทำใน module สถิติ:

```python
import numpy as np
import scipy.stats as stats

n_organic, r_organic = 1240, 278   # ลูกค้า, คนที่กลับมาซื้อเดือนถัดไป
n_promo, r_promo = 219, 16

p_pool = (r_organic + r_promo) / (n_organic + n_promo)
se = np.sqrt(p_pool * (1 - p_pool) * (1 / n_organic + 1 / n_promo))
z_stat = (r_organic / n_organic - r_promo / n_promo) / se
p_value = stats.norm.sf(abs(z_stat)) * 2
```

ได้ `z = 5.14` และ `p-value ≈ 0.00000027` — เล็กกว่า 0.05 มาก แปลว่าความต่างนี้ไม่ใช่ความบังเอิญ
จากการสุ่ม ข้อสรุปเรื่องคุณภาพของช่องทาง `promo` จึงยืนอยู่ได้

ตรวจไขว้ด้วย chi-square test อีกทางได้ผลสอดคล้องกัน (`chi2 = 25.49`, `p ≈ 0.00000044`)
— สองวิธีที่คิดคนละมุมแล้วให้คำตอบเดียวกันคือสัญญาณที่ดี

**ข้อควรระวังที่ต้องเขียนกำกับ:** ช่องทางไม่ได้ถูกสุ่ม (นี่ไม่ใช่การทดลอง) ดังนั้นสถิติบอกได้แค่ว่า
"ความต่างนี้ไม่น่าจะมาจากการสุ่ม" ไม่ได้พิสูจน์ว่า "ช่องทาง promo ทำให้ลูกค้าไม่กลับมา" —
อาจเป็นเพราะคนที่ตอบสนองต่อส่วนลดหนักๆ เป็นคนละกลุ่มกันตั้งแต่แรกก็ได้ (เรื่อง correlation ≠ causation
จาก module สถิติ บทที่ 6)

## 4. ความทนต่อ outlier

ลูกค้าคนเดียวที่ซื้อ 98,881 บาทอาจดันตัวเลขทั้งกลุ่มได้ ถ้าข้อสรุปขึ้นกับคนไม่กี่คน มันเปราะเกินกว่าจะเสนอ
วิธีตรวจที่เร็วที่สุดคือ **ตัดส่วนบนสุดออกแล้วคำนวณใหม่**:

| ข้อมูลที่ใช้ | รายได้จากลูกค้าใหม่ |
| --- | --- |
| ลูกค้าทั้งหมด | 84.0% |
| ตัดลูกค้าที่จ่ายสูงสุด 1% ออก | 83.6% |

แทบไม่ขยับ แปลว่าข้อสรุปไม่ได้มาจากลูกค้าไม่กี่คน ถ้าตัวเลขเปลี่ยนไปเยอะ (เช่น เหลือ 60%)
ต้องเขียนในรายงานว่าผลขึ้นกับลูกค้ารายใหญ่ไม่กี่ราย ซึ่งเป็นข้อมูลสำคัญสำหรับคนตัดสินใจ

## ใช้เครื่องมือคนละตัวคำนวณซ้ำ

การตรวจที่ง่ายแต่ได้ผลมากอีกอย่างคือคำนวณตัวเลขสำคัญซ้ำด้วยเครื่องมืออีกตัว เช่นตัวเลขที่ได้จาก SQL
ลองคำนวณซ้ำด้วย pandas:

```python
import pandas as pd

orders = pd.read_csv("data/orders.csv", parse_dates=['order_date'])
items = pd.read_csv("data/order_items.csv")
items['line'] = items['quantity'] * items['unit_price']
sales = items.merge(orders, on='order_id')
sales = sales[sales['status'] == 'completed']
revenue_2025 = sales[sales['order_date'].dt.year == 2025]['line'].sum()
```

ถ้าได้ 17,829,346 ตรงกับ SQL แปลว่าโอกาสที่ทั้งสองฝั่งจะผิดเหมือนกันพอดีนั้นต่ำมาก
การตรวจแบบนี้จับ bug ประเภท "join แล้วแถวซ้ำ" ได้ดีที่สุด เพราะวิธีเขียนของสองเครื่องมือต่างกันมากพอ

## สรุปสิ่งที่ต้องเขียนลงรายงาน

หลังตรวจครบทั้งสี่แบบแล้ว สิ่งที่ควรมีในรายงานคือ:

- ข้อสรุปหลัก พร้อมตัวเลขและนิยามที่ใช้
- ผลการตรวจความไวต่อนิยาม (บอกว่าเปลี่ยนนิยามแล้วได้เท่าไหร่)
- ผลทดสอบนัยสำคัญของความต่างที่สำคัญที่สุด
- ข้อจำกัด — โดยเฉพาะเรื่องที่ข้อมูลบอกความสัมพันธ์ได้แต่บอกสาเหตุไม่ได้

การเขียนสี่ข้อนี้ใช้พื้นที่ไม่ถึงครึ่งหน้า แต่เป็นสิ่งที่แยก "รายงานที่เชื่อถือได้" ออกจาก "ตัวเลขชุดหนึ่ง"
