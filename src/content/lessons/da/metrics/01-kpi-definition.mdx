## ตัวชี้วัดคือภาษาที่ทีมใช้คุยกัน

module ที่ผ่านมาสอนวิธี "ดึงตัวเลขออกมา" (SQL/pandas) และ "อ่านตัวเลขให้ถูก" (สถิติ/visualization)
module นี้ตอบคำถามที่มาก่อนหน้านั้นทั้งหมด — **จะวัดอะไร และวัดยังไงให้ทุกคนในทีมเข้าใจตรงกัน**

ตัวชี้วัด (metric) ที่ใช้งานได้จริงมี 3 คุณสมบัติ:

1. **มีนิยามเดียว** — ถามใครในทีมก็ตอบเหมือนกันว่า "ยอดขายเดือนนี้" นับจากอะไรบ้าง
2. **เทียบได้** — เดือนนี้เทียบเดือนที่แล้วได้ เพราะคิดด้วยกติกาเดียวกันทุกเดือน
3. **ชี้ทางต่อได้ (actionable)** — ถ้าตัวเลขแย่ลง พอจะรู้ว่าต้องไปดูอะไรต่อ

**KPI** (Key Performance Indicator) คือตัวชี้วัดกลุ่มเล็กๆ ที่ทีมตกลงกันว่าจะใช้ตัดสินว่างาน "ไปได้ดีหรือไม่"
ร้านค้าออนไลน์ในเว็บนี้มี KPI หลักไม่กี่ตัว: รายได้ (revenue), จำนวนออเดอร์ (orders),
ยอดเฉลี่ยต่อออเดอร์ (AOV — Average Order Value) และจำนวนลูกค้าที่ซื้อจริง

## นิยามที่คลุมเครือทำให้ตัวเลขผิดได้ทั้งรายงาน

คำว่า "ยอดขายเดือนนี้" ฟังดูชัดเจน แต่ลองแยกยอดขายตามสถานะออเดอร์ดู:

| status | รายได้ |
| --- | --- |
| completed | 32,531,978 |
| cancelled | 2,263,829 |
| returned | 1,738,543 |

ถ้ารายงานไม่ระบุว่านับสถานะไหนบ้าง คนหนึ่งอาจรวมทุกสถานะ (36,534,350) อีกคนนับเฉพาะ `completed`
(32,531,978) — ต่างกัน **12.3%** ทั้งที่ใช้ข้อมูลชุดเดียวกัน ในเว็บนี้เราตกลงกติกาว่า
**"รายได้" นับเฉพาะออเดอร์ `completed` เท่านั้น** (ออเดอร์ที่ถูกยกเลิกหรือคืนของ ไม่ใช่เงินที่ร้านได้จริง)
และทุกบทต่อจากนี้จะใช้กติกาเดียวกันนี้ตลอด

งานจริงก็เหมือนกัน: ก่อนเขียน query ต้องรู้ก่อนว่านิยามของตัวเลขคืออะไร ไม่ใช่เดาเอาเอง —
และเมื่อตกลงแล้วต้องเขียนไว้ที่ไหนสักแห่งให้ทั้งทีมอ่านได้ (เรียกว่า metric definition หรือ data dictionary)

## กับดักที่เจอบ่อยที่สุด: นับแถวหลัง JOIN

รายได้ต่อออเดอร์อยู่ในตาราง `order_items` (หนึ่งออเดอร์มีได้หลายรายการสินค้า) เวลา join กับ `orders`
จำนวนแถวจะกลายเป็นจำนวน **รายการสินค้า** ไม่ใช่จำนวนออเดอร์อีกต่อไป:

```sql
SELECT count(*) AS wrong_orders, count(DISTINCT o.order_id) AS orders
FROM orders o
JOIN order_items li ON li.order_id = o.order_id
WHERE o.status = 'completed'
```

`count(*)` ได้ `10,964` ส่วน `count(DISTINCT o.order_id)` ได้ `6,232` — ต่างกันเกือบสองเท่า
ถ้าเผลอใช้ `count(*)` เป็นจำนวนออเดอร์ AOV ก็จะเพี้ยนตามไปด้วยทันที (เพราะ AOV = รายได้ ÷ จำนวนออเดอร์)

**กติกาง่ายๆ:** หลัง join แล้วจะนับอะไร ให้ถามตัวเองก่อนว่า "หนึ่งแถวในผลลัพธ์นี้คืออะไร" —
ถ้าหนึ่งแถวคือหนึ่งรายการสินค้า แต่เราอยากนับออเดอร์ ต้องใช้ `count(DISTINCT ...)` เสมอ

## ตาราง KPI รายเดือน

KPI ส่วนใหญ่คำนวณจาก CTE ชั้นเดียวที่สรุปข้อมูลระดับเดือนก่อน แล้วค่อยหารต่อ:

```sql
WITH monthly AS (
  SELECT DATE_TRUNC('month', o.order_date) AS month,
         SUM(li.quantity * li.unit_price) AS revenue,
         COUNT(DISTINCT o.order_id) AS orders,
         COUNT(DISTINCT o.customer_id) AS customers
  FROM orders o
  JOIN order_items li ON li.order_id = o.order_id
  WHERE o.status = 'completed'
  GROUP BY 1
)
SELECT month, revenue, orders, ROUND(revenue / orders, 2) AS aov
FROM monthly
ORDER BY month
```

`AOV = revenue / orders` เป็นตัวอย่างของ **derived metric** (ตัวชี้วัดที่คำนวณจากตัวชี้วัดอื่น)
ข้อดีของการแยก CTE แบบนี้คือ ถ้าวันหนึ่งนิยาม "รายได้" เปลี่ยน (เช่น ต้องหักส่วนลด) แก้ที่เดียวใน CTE
แล้วตัวเลขที่คำนวณต่อจากมันจะถูกต้องตามไปด้วยทั้งหมด

## รายได้ก่อนหักส่วนลด vs หลังหักส่วนลด

ตาราง `orders` มีคอลัมน์ `discount_pct` (ว่างแปลว่าไม่มีส่วนลด) — รายได้ที่ร้านได้จริงคือ
ยอดหลังหักส่วนลด ซึ่งคิดได้ด้วย `COALESCE(discount_pct, 0)`:

```sql
SELECT ROUND(SUM(li.quantity * li.unit_price), 2) AS gross_revenue,
       ROUND(SUM(li.quantity * li.unit_price * (1 - COALESCE(o.discount_pct, 0) / 100.0)), 2) AS net_revenue
FROM orders o
JOIN order_items li ON li.order_id = o.order_id
WHERE o.status = 'completed'
```

ได้ `gross = 32,531,978` และ `net = 31,618,043.10` — ต่างกัน 2.8% ตัวเลขทั้งสองถูกทั้งคู่
แต่ตอบคนละคำถาม (ยอดขายตามป้ายราคา vs เงินที่เข้าร้านจริง) **ประเด็นไม่ใช่ว่าอันไหนถูก
แต่คือรายงานต้องบอกให้ชัดว่ากำลังพูดถึงอันไหน** — และทั้งบทต่อจากนี้เราใช้ตัวที่ยังไม่หักส่วนลด (gross)
เพื่อให้เทียบกับบทก่อนๆ ได้ ยกเว้นข้อที่บอกไว้ชัดเจนว่าให้หักส่วนลด

## การเติบโตเทียบเดือนก่อนหน้า (MoM)

ตัวเลขเดี่ยวๆ ไม่บอกอะไรจนกว่าจะมีอะไรให้เทียบ วิธีเทียบที่ใช้บ่อยที่สุดคือ **MoM (month over month)** —
เทียบกับเดือนก่อนหน้าด้วย `LAG()`:

```sql
WITH monthly AS (...)
SELECT month, revenue,
       ROUND((revenue - LAG(revenue) OVER (ORDER BY month))
             / LAG(revenue) OVER (ORDER BY month) * 100, 1) AS mom_pct
FROM monthly
ORDER BY month
```

เดือน พ.ย. 2025 ได้ `+60.7%` ซึ่งดูน่าตกใจ แต่ข้อมูลชุดนี้มีฤดูกาลชัดเจน (ช่วงปลายปีคนซื้อเยอะ)
ทุกเดือน พ.ย.–ธ.ค. จึงกระโดดขึ้นเป็นปกติ — การเทียบกับ **เดือนเดียวกันของปีก่อน (YoY)** จึงมักยุติธรรมกว่า
สำหรับธุรกิจที่มีฤดูกาล ส่วน MoM เหมาะกับการจับความเปลี่ยนแปลงระยะสั้นมากกว่า
