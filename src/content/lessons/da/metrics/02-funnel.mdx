## funnel คืออะไร

ลูกค้าไม่ได้เดินเข้ามาซื้อของในก้าวเดียว แต่ผ่านหลายขั้น — เข้าเว็บ ดูสินค้า ใส่ตะกร้า กดไปหน้าจ่ายเงิน
แล้วจึงจ่ายจริง แต่ละขั้นมีคนหายไปเสมอ ภาพที่ได้จึงเหมือนกรวย (funnel) ที่แคบลงเรื่อยๆ

**funnel analysis** คือการนับว่าแต่ละขั้นเหลือคนเท่าไหร่ เพื่อหาว่า "คนหายไปมากที่สุดตรงไหน" —
เพราะจุดนั้นคือจุดที่การแก้ไขให้ผลตอบแทนสูงที่สุด

ตาราง `events` ในเว็บนี้มีคอลัมน์ `event_type` ที่เป็นขั้นของ funnel พอดี เรียงตามลำดับจริงดังนี้:

`visit` → `view_product` → `add_to_cart` → `checkout` → `purchase`

และหน่วยที่เรานับคือ **session** (คอลัมน์ `session_id`) — หนึ่ง session คือการเข้าเว็บหนึ่งครั้ง

## หน่วยของการนับต้องเลือกให้ถูกก่อนเขียน query

ก่อนนับอะไร ต้องตอบก่อนว่า "หนึ่งหน่วยของ funnel นี้คืออะไร" — session, ผู้ใช้ (user) หรือออเดอร์
ในเว็บนี้เรานับเป็น **session** เพราะข้อมูล `events` มี `customer_id` เป็นค่าว่างถึง 22,448 event
จากทั้งหมด 55,900 (ผู้ใช้ที่ยังไม่ล็อกอินหรือยังไม่เคยสมัคร) — ถ้านับเป็นผู้ใช้จะทิ้งข้อมูลเกือบครึ่งไปเปล่าๆ

การเลือกหน่วยไม่มีคำตอบตายตัว แต่ต้องเลือกให้เหมือนกันทุกขั้นของ funnel เดียวกัน
เทียบ "จำนวน session ที่ดูสินค้า" กับ "จำนวนผู้ใช้ที่จ่ายเงิน" ในตารางเดียวกันไม่ได้ ต่อให้ตัวเลขทั้งสองถูกก็ตาม

## นับ session ของแต่ละขั้น

```sql
SELECT event_type, COUNT(DISTINCT session_id) AS sessions
FROM events
GROUP BY 1
```

ผลลัพธ์ถูกต้องแล้ว แต่มีปัญหาหนึ่งที่เห็นทันทีเมื่อเอาไปให้คนอ่าน: `GROUP BY` เรียงผลลัพธ์ตามตัวอักษร
(`add_to_cart`, `checkout`, `purchase`, `view_product`, `visit`) ซึ่ง **ไม่ใช่ลำดับของ funnel เลย**
funnel ที่เรียงผิดลำดับอ่านไม่รู้เรื่อง เพราะสายตาคนอ่านคาดหวังกรวยที่แคบลงเรื่อยๆ

วิธีแก้คือใส่หมายเลขขั้นเข้าไปเองด้วย `CASE`:

```sql
SELECT CASE event_type
         WHEN 'visit' THEN 1
         WHEN 'view_product' THEN 2
         WHEN 'add_to_cart' THEN 3
         WHEN 'checkout' THEN 4
         WHEN 'purchase' THEN 5
       END AS step_no,
       event_type,
       COUNT(DISTINCT session_id) AS sessions
FROM events
GROUP BY 1, 2
ORDER BY step_no
```

ได้ funnel จริงของข้อมูลชุดนี้:

| ขั้น | sessions | % ของ visit |
| --- | --- | --- |
| visit | 28,000 | 100.00% |
| view_product | 16,783 | 59.94% |
| add_to_cart | 5,800 | 20.71% |
| checkout | 3,178 | 11.35% |
| purchase | 2,139 | 7.64% |

## สองมุมมองของ conversion rate — ต้องบอกเสมอว่าหารด้วยอะไร

ตัวเลข conversion ของ funnel มีสองแบบที่ใช้กันทั้งคู่ และมักถูกสลับกันจนสื่อสารผิด:

- **% ของขั้นก่อนหน้า (step conversion)** — จากคนที่มาถึงขั้นนี้ ไปต่อได้กี่ %
- **% ของขั้นแรก (overall conversion)** — จากคนที่เข้าเว็บทั้งหมด มาถึงขั้นนี้กี่ %

| ขั้น | % ของขั้นก่อนหน้า | % ของ visit |
| --- | --- | --- |
| view_product | 59.94% | 59.94% |
| add_to_cart | 34.56% | 20.71% |
| checkout | 54.79% | 11.35% |
| purchase | 67.31% | 7.64% |

ตัวเลขเดียวกันทั้งตาราง แต่เล่าคนละเรื่อง: ขั้น `add_to_cart` ผ่านไปได้แค่ 34.56% ของคนที่ดูสินค้า —
**นี่คือจุดที่คนหายไปเยอะที่สุดของ funnel นี้** (หายไป 65.44% ในขั้นเดียว) ส่วน `purchase` ที่ดูน้อยนิด
เมื่อเทียบกับ visit (7.64%) จริงๆ แล้วเป็นขั้นที่ผ่านได้ดีที่สุด (67.31% ของคนที่มาถึงหน้าจ่ายเงิน)

การพูดว่า "conversion 7.64%" โดยไม่บอกว่าหารด้วยอะไรจึงกำกวมมาก ต้องพูดให้ครบว่า
"7.64% ของ session ที่เข้าเว็บจบด้วยการซื้อ"

## คำนวณ step conversion ด้วย LAG

เมื่อมีตาราง funnel เรียงตามขั้นแล้ว `LAG()` ดึงจำนวนของขั้นก่อนหน้ามาคำนวณต่อได้เลย:

```sql
WITH funnel AS (
  SELECT CASE event_type
           WHEN 'visit' THEN 1 WHEN 'view_product' THEN 2 WHEN 'add_to_cart' THEN 3
           WHEN 'checkout' THEN 4 WHEN 'purchase' THEN 5
         END AS step_no,
         event_type,
         COUNT(DISTINCT session_id) AS sessions
  FROM events
  GROUP BY 1, 2
)
SELECT step_no, event_type, sessions,
       ROUND(sessions * 100.0 / LAG(sessions) OVER (ORDER BY step_no), 2) AS pct_of_prev,
       ROUND(sessions * 100.0 / MAX(sessions) OVER (), 2) AS pct_of_visit
FROM funnel
ORDER BY step_no
```

`MAX(sessions) OVER ()` (window ที่ไม่มี `PARTITION BY` และไม่มี `ORDER BY`) คือค่าสูงสุดของทั้งตาราง
ซึ่งก็คือจำนวน session ของขั้นแรก — ใช้เป็นตัวหารของ `pct_of_visit` ได้โดยไม่ต้องเขียน subquery แยก

## แบ่งกลุ่มดู (segment) — และเมื่อผลออกมาว่า "ไม่ต่าง"

funnel รวมบอกว่าปัญหาอยู่ขั้นไหน แต่ไม่บอกว่าเกิดกับใคร ขั้นต่อไปคือแบ่งกลุ่มดู เช่นตามอุปกรณ์:

| device | visit | purchase | conversion |
| --- | --- | --- | --- |
| mobile | 18,168 | 1,404 | 7.73% |
| desktop | 9,832 | 735 | 7.48% |

ต่างกันแค่ 0.25 จุดเปอร์เซ็นต์ และเมื่อดูทีละขั้นก็แทบทับกันสนิท (เช่นขั้น `add_to_cart` ได้ 34.78% บน mobile
และ 34.16% บน desktop) — **นี่ก็เป็นคำตอบที่ใช้งานได้เหมือนกัน**: ปัญหาที่ขั้น `add_to_cart`
ไม่ได้เกิดจากอุปกรณ์ ทีมจึงไม่ต้องเสียเวลาไปไล่แก้ responsive design แต่ควรไปดูตัวหน้าสินค้าหรือราคาแทน

ผลที่ออกมาว่า "ไม่ต่าง" ไม่ใช่การวิเคราะห์ที่ล้มเหลว มันคือการตัดสมมติฐานหนึ่งออกไป ซึ่งมีค่าพอๆ กับการเจอความต่าง

## ระวังตอนเทียบ conversion ข้ามช่วงเวลา

conversion rate รายเดือนของข้อมูลชุดนี้อยู่ราว 6.2–8.3% แต่เดือน ส.ค.–ก.ย. 2025 มี session มากกว่าเดือนอื่น
ถึง 7 เท่า (8,212 และ 7,788 เทียบกับราว 1,200 ในเดือนปกติ) เพราะเป็นช่วงที่มีการทดลอง A/B test
(บทที่แล้วใน module สถิติ) — เวลาเห็นตัวเลขกระโดดแบบนี้ ต้องถามก่อนเสมอว่า
**"จำนวนคนที่เข้ามาเปลี่ยนไปหรือเปล่า และเป็นคนกลุ่มเดิมไหม"** ก่อนจะสรุปว่า conversion ดีขึ้นหรือแย่ลง
เพราะ traffic ที่มาจากคนละที่มามักมีพฤติกรรมต่างกัน
